# Netlify 顧客端交接指南

這份文件供日後修改既有顧客端 `https://fanciful-pegasus-e051a5.netlify.app/` 時使用。本 repository **沒有修改、重新部署或搬遷該網站**。

## 問卷映射

既有三步驟診斷的資料應轉成共用的 `CustomerNeeds`：

| 顧客端欄位 | 對應欄位 | 注意事項 |
| --- | --- | --- |
| 寵物類型／數量 | `petTypes`, `petCount` | 可為空，未來支援非毛孩情境。 |
| 獨處時間 | `aloneHours` | 使用顯示值，例如 `6–8 小時`。 |
| 困擾 | `painPoints` | 多選陣列，勿混入自由聯絡資訊。 |
| 預算 | `budgetRange` | `尚未決定` 合法。 |
| 現有設備 | `existingDevices` | 應保存型號待確認的事實，不自行推論規格。 |
| 環境與其他備註 | `housingType`, `extraNotes` | 避免要求非必要個資。 |

## 診斷結果新增 CTA

保留既有複製、列印與售後資訊。在結果區加入：

1. **預約門市顧問**：開啟表單，收集示範門市、偏好日期、偏好時段、必要聯絡方式與資料提供同意。
2. **取得需求編號**：提交匿名需求，讓使用者保存後續查詢所需的私有憑證。

表單應對必填欄位、日期合法性與同意欄位做驗證。資料必須交給受保護的後端，而非直接寫入前端 localStorage 或 GitHub Pages。

## 建立與查詢契約

- 後端建立 `caseId`（不可猜測 UUID）與展示用 `caseCode`；展示代碼不是驗證密碼。
- 提交預約後只能是 `requested`，結果頁顯示「等待店員確認」，絕不可寫「預約成功」。
- `contactReference`、同意時間與可辨識資訊不得在網址、analytics event 或公開 API 回應中外洩。
- 顧客查詢狀態需要不可猜測的私有查詢憑證或已驗證身分；不得只靠流水案件編號讀取其他人的需求或聯絡資料。
- 後端需驗證欄位、執行 rate limit、限制 CORS origin，並以 RLS／等效權限讓店員只讀取獲授權的門市與案件。

## 尚未接後端時

按鈕應明確顯示「示範流程」或「服務尚未開放」，不要製造假成功。這個 GitHub Pages 店員端包含同情境的 `EL-001`，僅供展示完整流程，**不會**因 Netlify 端送出資料而自動同步。
